## FIX 1 — Tide Pool wipe guard (P0 — the data-loss bug)

**File:** App.jsx, `TidePoolSection`, the reset effect at ~1159.

**Root cause (verified):** the bare fallback at 1146 has no `choreLastReset`, so
on any mount where `coveData` hasn't hydrated (slow pull, failed pull, 401 loop),
`lastReset = ""` ≠ today → the effect **pushes a bare record with empty arrays**
(`sKidIdx2 === -1` always pairs with the fallback — same predicate as `find`),
destroying the server's real data. This produced the exact blob observed in
production.

**The fix — one line.** Only reset records that actually exist. A record that
isn't in `coveData` has nothing to reset; the reset path must never be the thing
that *creates* (and persists) a record.

```
OLD (App.jsx ~1159):
  React.useEffect(function(){
    if(!sKidData) return;
    var lastReset = sKidData.choreLastReset || "";

NEW:
  React.useEffect(function(){
    if(!sKidData) return;
    // Wipe guard: only reset records that actually exist in coveData. When the
    // kid has no saved record (sKidIdx2 < 0), sKidData is the bare in-memory
    // fallback — persisting it from here would push {chores:[],treasures:[],
    // shells:0} over the server's real data whenever this mounts before the
    // household pull has landed (slow pull, failed pull, expired auth). That is
    // the confirmed Tide Pool wipe. A record gets created only by a real user
    // action (add chore/treasure), never by the reset.
    if(sKidIdx2 < 0) return;
    var lastReset = sKidData.choreLastReset || "";
```

**Note for the record:** this closes the *automatic* wipe. A residual risk
remains if a user manually adds a chore while `coveData` is un-hydrated (their
add pushes a 1-kid array over a fuller server array) — that's the broader
hydration-signal question, logged, not solved here. The automatic path is the
one that fired in production.

## FIX 2 — Chore reset uses UTC, fires ~6h early (both sites)

**Verified:** production blob had `choreLastReset:"2026-07-17"` written at
20:47 *local* on the 16th — only possible if "today" is computed in UTC.
`.toISOString()` is always UTC. F-66/F-67 fixed staleness, not the frame.

**Site A — App.jsx ~1158 (TidePoolSection):**
```
OLD:
  var todayStr = new Date().toISOString().split("T")[0];
NEW:
  // Local calendar date, not UTC — .toISOString() is UTC and flips "today" at
  // ~6pm Mountain, resetting chores hours early (verified from production
  // blob timestamps). padStart is ES2017 — fine for the ES2019 target.
  var _tpNow = new Date();
  var todayStr = _tpNow.getFullYear() + "-" + String(_tpNow.getMonth()+1).padStart(2,"0") + "-" + String(_tpNow.getDate()).padStart(2,"0");
```

**Site B — App.jsx ~8563 (TidePoolTab checkReset):**
```
OLD:
      function checkReset(){
        var todayStr = new Date().toISOString().split("T")[0];
NEW:
      function checkReset(){
        // Local date, not UTC — same fix as TidePoolSection. See F-66/F-67 note.
        var _n = new Date();
        var todayStr = _n.getFullYear() + "-" + String(_n.getMonth()+1).padStart(2,"0") + "-" + String(_n.getDate()).padStart(2,"0");
```

**Do NOT change** the other `toISOString().split("T")[0]` sites (3642, 3687,
4028, 5659…) in this pass — several compare against `calEvents.date` values that
may themselves have been written in UTC, and flipping only the read side would
desync them. Log as a follow-up sweep: "audit every date-string comparison for
UTC/local frame agreement." Changing them piecemeal here risks a new F-17.

*(Claude Code: also check whether a `localDateStr()` helper already exists —

## FIX 8 — Mobile: dash screens scroll sideways (bug #12 / #21)

Can't render, so this is the two highest-probability mechanical fixes plus a
30-second locator for anything left.

**The mechanism:** grid/flex children default to `min-width:auto`, so any
`whiteSpace:"nowrap"` descendant forces its track wider than the viewport → the
whole page scrolls sideways. Ellipsis only works once the cell can shrink.

**8a — calendar week/day cells and glance rows: add `minWidth:0`.** Verified
nowrap-without-shrink sites: App.jsx **6176** (`Hours` span's flex row), **6262**
(person-name span, no overflow control — add `overflow:"hidden",
textOverflow:"ellipsis", minWidth:0` to it), and audit the flex parents of
5872/5885/5940/6096 — each nowrap child's flex parent needs `minWidth:0` on the
flexed child. Claude Code: for each of those six sites, add `minWidth:0` to the
element carrying `flex:1` (or the nowrap element itself where it's the direct
grid/flex child).

**8b — app-shell clamp (safety net).** In the global style block (the one
defining `.fu` etc. — grep `"@keyframes"` or the first `<style>` in App.jsx),
add:
```
html, body { overflow-x: hidden; width: 100%; }
```
This cannot break vertical layout and stops any residual offender from scrolling
the page itself. It masks rather than fixes — which is why 8a comes first — but
on a family PWA, "page never scrolls sideways" is the correct guarantee.

**8c — find any remaining offender (you, on the phone-size viewport, 30 sec):**
DevTools → toggle device toolbar → iPhone size → open the offending dash → paste:
```js
[...document.querySelectorAll('*')].filter(el => el.scrollWidth > document.documentElement.clientWidth + 1)
  .slice(0,10).map(el => ({tag: el.tagName, cls: el.className, w: el.scrollWidth, text: (el.textContent||"").slice(0,40)}))
```
That names the exact elements wider than the viewport. Send me the output if 8a
didn't already cover them, and I'll write the specific fix.

**AnchorVault:** its `overflowX:"auto"` rows (684, 756, 2913, 4008, 4863) are
*intentional* scrollable tab strips — correct on mobile, leave them. The
`repeat(3,1fr)` at 1461 is fine (1fr shrinks). Nothing to change there without
8c evidence.
