### Critical — F-06 and F-11 CLOSED at `e5ccd83` (2026-07-16); history preserved below
- **F-06 — CLOSED at `e5ccd83` (2026-07-16). Was Critical, OPEN at `174b06e`.** **History:** `App.jsx:1668–1677` (current line numbers at the time; was 1656–1666 at fa9e703). Export Backup handler unconditionally did `Object.keys(localStorage).forEach(k => { if(k.startsWith("af_")) data[k] = ... })` — no exclusion list — then downloaded the blob as `anchor-flow-backup-<date>.json`, which commonly auto-syncs to iCloud. This dumped the live `af_authToken` (Supabase JWT) and `af_health_pin` (plaintext, no expiry) plus all children's PII. **Named in commit message(s) among `a7f4579`/`a71c5a2`/`2a414db`/`366ced0` — none of those diffs touched this handler.** **First fix attempt, `4a84767` — did not actually close it.** It excluded three named keys (`af_authToken`, `af_authUser`, `af_health_pin`) taken from this audit document's own prior write-up. Verified by exporting a real backup from a deployed build (`20260716-032234-70fd776`): the export still contained the full Supabase SDK session (`af_supabase_session`, including the refresh token — see Part H), a duplicate JWT (`af_token`), and a Google Calendar OAuth token (`af_googleCalToken`). None of the three excluded key names were even the real leak. Session 1's original basis for this finding — that the refresh token lived in a separate `sb-*`-prefixed key, out of reach of the `af_` scan — was factually wrong; the whole session, refresh token included, lives under `af_supabase_session`, which *is* `af_`-prefixed, because `src/lib/supabase.js` sets `storageKey: "af_supabase_session"`. That means the exposure was persistent-account-takeover, not the ~1hr access-token window originally assumed. **Real fix, `e5ccd83` (2026-07-16) — allow-list, not deny-list.** Export now includes only keys whose bare name is in `SYNC_KEYS` or the (currently empty) `SAFE_LOCAL_PREFS`; everything else, named or not, known or not, is excluded by construction. **Verified by reading a real export from `20260716-180902-e5ccd83`:** contained only `af_calEvents`, `af_compassCache`, `af_tasks`, `af_exhale_groups`, `af_mealsWeekOf` — all real `SYNC_KEYS` data, zero credentials. See **Part H** for the full credential inventory and the argument for why a deny-list built from source alone could never have been complete.
- **F-11 — CLOSED at `e5ccd83` (2026-07-16). Was Critical, OPEN at `174b06e`.** **History:** `App.jsx:1678–1712` (current at the time; was 1678–1697 at fa9e703). Import Backup called raw `window.confirm(...)` — silently auto-suppressed on iOS standalone PWA (returns `true`, no dialog shown) — then wrote every `af_*` key from the file, including `af_authToken`, to `localStorage` via `keys.forEach(k => localStorage.setItem(k, data[k]))` with only a `keys.length < 5` sanity check. Reload authenticated as the injected session: complete silent account takeover in one tap past the file picker. **`4a84767` fixed the dialog half only** — replaced `window.confirm`/the four `alert()` calls with `afConfirm`/`showInAppBanner`, correctly matching the F-19/F-52 pattern — **but not the payload half.** The import write-loop used the same deny-list as export, so a crafted backup file containing `af_supabase_session` (or `af_token`, or `af_googleCalToken`) would still have been written straight to `localStorage` on import, restoring an attacker-controlled session into the victim's browser — the exact attack this finding describes, just gated behind a now-visible confirmation dialog instead of a silent one. **F-11 was therefore NOT actually closed at `4a84767`**, despite the fix being explicitly scoped to it; the dialog became visible, the payload stayed unfiltered. **Real fix, `e5ccd83` (2026-07-16).** The same allow-list now governs import: `SYNC_KEYS` entries go through `sanitizeHouseholdData` (unchanged mapping from `4a84767`); `SAFE_LOCAL_PREFS` entries write through directly (empty today); everything else in an uploaded file — credential or otherwise, named or not — is silently dropped. See **Part H**.

## PART G — F-95 (Critical, independently reported and confirmed 2026-07-15)

> Reported directly (password reset appeared to just log the user in, no reset form), not found by any audit pass. Confirmed by reading the code end to end. Its own cluster (**Cluster I**, below) — this is not a sync-write bug, a hardcoded-data bug, or a native-dialog bug like the other clusters; it's a component-initialization-order race between two independently-correct halves of the same feature.

- **F-95 — Critical.** `App.jsx:12154–12171` (root cause — `onAuthStateChange` never inspects `event`), `App.jsx:3424–3438` (the dead detection logic this should be driving), `App.jsx:11794` (the render gate this leaves permanently closed). **Why:** Supabase's client is configured with `detectSessionInUrl: true` (`src/lib/supabase.js`), so when a user clicks a password-recovery email link, the SDK automatically parses the `access_token`/`type=recovery` pair out of the URL hash, establishes a real session from it, fires a distinct `PASSWORD_RECOVERY` event through `onAuthStateChange`, and — per its documented behavior — clears the hash from the URL as a side effect of that same processing. `onAuthStateChange`'s handler (`App.jsx:12154`) captures the `event` parameter but only ever compares it to `"SIGNED_OUT"`; it never checks for `"PASSWORD_RECOVERY"`. Since the resulting session is truthy, `App()`'s top-level gate (`if (!session) return <AuthScreen/>`, `App.jsx:12181`) is skipped and the user is dropped straight into `HomeFlow` — fully authenticated, no password form shown. The app's *only* recovery-link detection is a manual, lazy `useState(() => { check window.location.hash })` pair inside `HomeFlow` (`App.jsx:3426–3438`), which mounts strictly *after* the state change above — i.e., after Supabase's own client has already consumed and typically cleared that same hash. ## PART H — Credential inventory and the allow-list fix (2026-07-16, found while re-verifying F-06/F-11)

> `4a84767`'s deny-list was built from this audit document's own prior key names, never checked against a real export. It was wrong. This section documents what a real export actually contained, why a deny-list built from reading current source can never be complete, and the meta-pattern this closure shares with F-95 and F-63.

### Real credential keys found (verified against a live export, not source-reading alone)

- **`af_supabase_session`** — not written by application code at all; `src/lib/supabase.js` configures the Supabase client with `storageKey: "af_supabase_session"`, and the SDK persists its **entire session object** there — `access_token`, `refresh_token`, `expires_at`, `token_type`, and the full `user` object (id, email, metadata) — confirmed by reading the installed `@supabase/auth-js` source (`_saveSession()`), which writes the complete session under one key whenever no separate `userStorage` is configured (it isn't, here). Because the configured key name happens to start with `af_`, the blanket prefix scan swept it up whole. **This corrects Session 1's original F-06 reasoning, which held that the refresh token lived in a separate `sb-*`-prefixed key outside the scan's reach — that was factually wrong.** The refresh token was always inside the `af_` prefix scan's reach, meaning the exposure was a persistent account-takeover vector (refresh tokens are long-lived), not the ~1-hour access-token window the original write-up assumed.
- **`af_token`** (`App.jsx:12203`, inside `AuthScreen`'s `onAuth` callback) — a second, separate copy of the access-token JWT under a different key name, written on the line directly above the `af_authToken` write. Not read anywhere else in the file; a live duplicate, not dead code.
- **`af_googleCalToken`** — written via `useSaved("googleCalToken", null)` (`App.jsx:1993`, set at `App.jsx:10868`) — a Google Calendar OAuth access token.
- **`af_refreshToken`** — see below; not currently written by any live code path, but still found in a real export.

### Why the deny-list could never have worked: localStorage holds history that source-reading can't see

`App.jsx:12205-12207` contains `if (s.refresh_token) { }` — an empty conditional block. Someone clearly started to persist the refresh token under `af_refreshToken` at some point and the write body is gone now; grepping current source for `af_refreshToken` turns up zero active writes. And yet **a real export from a live build contained `af_refreshToken` anyway** — the key outlived the code that wrote it. No amount of re-reading `App.jsx` today can discover a key that current source doesn't reference at all; only reading what's actually sitting in a real user's `localStorage` can. This is the decisive argument for the allow-list over the deny-list, independent of the specific key-naming mistake in `4a84767`: a deny-list's completeness is bounded by what someone thought to grep for in the code that exists *right now*, and `localStorage` does not forget what earlier code wrote. An allow-list restricted to `SYNC_KEYS` (plus the empty `SAFE_LOCAL_PREFS`) ignores `af_refreshToken` — and anything else with a similar history — by construction, without anyone needing to know it exists.

### Meta-finding: the codebase already knew — this is the architectural pattern of the audit

`tests/unit/sanitize.test.js`'s own completeness lint ("A10") maintains a `DEVICE_LOCAL` set that already lists `authToken`, `authUser`, `refreshToken`, `householdId`, `householdOwnerId`, and `googleCalToken` — under the comment **"Auth & session — must never leave the device."** That knowledge existed in the repository the entire time this vulnerability was open. It was never consulted by the export/import code. The test enforces that every `useSaved()` key is *classified* somewhere; it says nothing about whether the backup feature respects that classification, and nothing connects the two.

This is not an isolated coincidence — it's the same shape as two other findings in this audit's record:
- **F-95** — `resetPasswordForEmail` (send) and `SetPasswordModal` (receive) are both independently correct, fully built, and never wired together; `onAuthStateChange` never checks for the one event (`PASSWORD_RECOVERY`) that would connect them.
- **F-63** (Session 3) — 2 of 10 `/api/claude` call sites correctly check `res.ok`; the other 8 don't, despite the correct pattern already existing in the same file.

Three separate findings, three separate features, the same underlying failure mode: **the correct piece of code (or knowledge) already exists somewhere in this codebase. The bug is never that nobody knew the right way to do it — it's that the right way was never connected to the place that needed it.** If Session 5 does root-cause ranking, this is arguably the single most important line item in the entire audit: the findings here aren't primarily about wrong code, they're about unconnected code — a lint, a helper, an event handler, a completeness check, all correct, all sitting a few files or a few hundred lines away from the exact place they were needed, unused.
